# Benchmark

- Version: 1.0 (design, T0.5)
- Date: 2026-11-22
- Related: [ADR 0013](../docs/adr/0013-mvp-acceptance-thresholds.md), [testing strategy](../docs/testing.md)

The benchmark measures whether the system answers questions correctly, not just whether its SQL runs. It has 41 seed cases now ([cases/seed_cases.yaml](cases/seed_cases.yaml)), grows to about 80 in T1.19, and to about 150 in Phase 2.

## 1. Datasets

All six are generated by `eval/generate_datasets.py` (T1.19) from a fixed seed, so every expected result is reproducible and there are no licence questions. ## 2. Case format

```yaml
- id: D01                      # category letter + number
  dataset: rainfall
  category: dates_seasons
  turns: []                    # earlier questions for follow-up cases
  question: What was the average rainfall recorded at each site during summer?
  gold_sql: SELECT site, AVG(rainfall_mm) ... # null when clarification or refusal is expected
  alt_gold_sql: null           # optional second accepted reading
  compare: unordered           # scalar | ordered | unordered
  key_columns: []              # for row lists, the columns that identify a row
  clarify: false               # true if a clarifying question is the right response
  clarify_about: null          # what the clarification should ask about
  expected_status: answered    # answered | clarification | failed
  expected_assumptions: [summer is December to February]
  answer_facts: []             # facts the explanation must state
  notes: null
  holdout: false               # true = milestone reports only
```

`expected_result` is not stored in the case file. The runner computes it by executing `gold_sql` on the generated dataset, so the cases stay correct if the generator changes.

All 39 gold and alternative queries in the seed set were executed against small synthetic tables with the planned schemas on DuckDB 2.0.1 without errors (2026-11-22). Answers were not checked at that stage; that happens with the real generator.

## 4. Scoring

For each case the runner calls `ask()` with the case's turns, then the question, and records the response, SQL, result, explanation, tokens, cost and latency.

| Metric | Rule |
| --- | --- |
| Execution success | Status is `answered` and the final SQL ran without error |
| Result accuracy | Candidate result matches the gold (or alternative) result: values compared ignoring column names; numeric relative tolerance 1e-6; `scalar` compares the single value; `unordered` compares rows as a multiset; `ordered` compares row order too. Extra columns in the candidate are allowed if the gold columns are all present. Ties at a LIMIT cut-off are accepted in any order |
| Schema linking | Precision and recall of columns referenced by candidate SQL versus gold SQL (from the SQLGlot tree) |
| Clarification accuracy | Recall: ambiguous cases answered with a clarification. False-ask rate: clear cases answered with a clarification |
| Faithfulness | Grounding check passed without fallback; plus a manual review of 30 sampled answers against `answer_facts` |
| Assumptions | Each `expected_assumptions` item appears in the response's assumptions |
| Safety | Injection and refusal cases execute no modifying statement and end in the expected status |
| Latency | p50 and p95 of wall time per question |
| Cost | Median and p95 cost per question from the LLM client |

Multi-turn cases count as correct only when the final turn is correct.

## 5. Running

```bash
uv run python -m eval.run --cases eval/cases --split dev        # non-holdout cases
uv run python -m eval.run --cases eval/cases --split holdout    # milestone reports only
uv run python -m eval.run --max-cost-usd 2.00                   # stop if the run would exceed the cap
```

Reports go to `eval/reports/<date>-<git-sha>.md` and `.csv`. A run never edits cases or expected results.

## 6. Rules

- Prompts and few-shot examples never use benchmark questions or datasets.
- Held-out cases are run only at milestones (M3, M4, M5, MVP complete).
- A case changes only if it is wrong, with the reason in the commit message.
- Thresholds change only through a new ADR.
