# Benchmark

- Version: 1.1 (harness built, T1.19)
- Date: 2026-11-23
- Related: [ADR 0013](../docs/adr/0013-mvp-acceptance-thresholds.md), [testing strategy](../docs/testing.md)

The benchmark measures whether the system answers questions correctly, not just whether its SQL runs. It has 80 cases now ([cases/](cases/)): the 41 seed cases of T0.5 and 39 added in T1.19. It grows to about 150 in Phase 2.

The harness is built and tested without a model. `uv run python -m eval.run --oracle` runs every case with a stand-in that answers with the gold SQL, which proves the datasets, the scoring and the validator work together (all 80 cases score as right, and no gold query is blocked). A run with a real model needs `OPENAI_API_KEY` and the two model names; see section 5.

## 1. Datasets

All six are generated by `eval/generate_datasets.py` from a fixed seed, so every expected result is reproducible and there are no licence questions (nothing here comes from a real person or organisation). Each is written in the messy form a real user would upload. The SQL names below are what the normaliser (T1.05) produces, so the benchmark also tests ingestion.

T1.19 checked this: all six files load through the application's own ingestion with exactly the SQL names and types in these tables (`tests/eval/test_datasets.py`), so no gold query needed changing. Two things to know:

- The files can be written out and uploaded by hand: `uv run python -m eval.generate_datasets --out eval/data` (the folder is ignored by git). Their names are the realistic ones given below.
- The runner loads each dataset under the name of its table (`sales.csv`, `survey.csv`, `rainfall.xlsx`, and so on), because the table name comes from the file name and the gold SQL reads `FROM sales`, not `FROM retail_sales`. The same bytes are loaded; only the name differs. For a workbook the runner names the sheet, though the data sheet is also the first one, so detection finds it unaided.

## 2. Case format

Cases are YAML files in [cases/](cases/): the runner reads every `*.yaml` there, in file name order. `seed_cases.yaml` is T0.5's 41 cases and `expansion_cases.yaml` is T1.19's 39. A file with any problem is refused whole, with every problem listed (`eval/cases.py`), so a typo cannot quietly remove a case from a run.

```yaml
- id: D01                      # category letter + number
  dataset: rainfall
  category: dates_seasons
  turns: []                    # earlier questions for follow-up cases
  question: What was the average rainfall recorded at each site during summer?
  gold_sql: SELECT site, AVG(rainfall_mm) ... # null when clarification or refusal is expected
  alt_gold_sql: null           # optional second accepted reading
  compare: unordered           # scalar | ordered | unordered
  key_columns: []              # for row lists, the columns that identify a row
  clarify: false               # true if a clarifying question is the right response
  clarify_about: null          # what the clarification should ask about
  expected_status: answered    # answered | clarification | failed
  expected_assumptions: [summer is December to February]
  answer_facts: []             # facts the explanation must state
  notes: null
  holdout: false               # true = milestone reports only
```

- `expected_result` is not stored. The runner computes it by running `gold_sql` (and `alt_gold_sql`) on the generated dataset, through the same validator and executor the application uses, so the cases stay correct if the generator changes. A gold query that the validator refuses or that fails to run makes the case *invalid*: the model is not asked, and the report lists it (ADR 0013 requires zero gold queries blocked).
- `expected_status` is `answered` by default and `clarification` when `clarify` is true. `failed` is for a refusal. A case that expects a question back or a refusal has no `gold_sql`.
- `compare: scalar` needs a 1 by 1 gold result. `ordered` needs an ORDER BY in the gold on columns that appear in its output (by name or number), which is how the order is checked.
- `alt_gold_sql` is for a second reading that is just as right (a month shown as a date or as `2024-03`, a department's budget for the year or for all years). Add one when a careful analyst could answer either way; do not add one to accept a mistake.
- `key_columns` names the columns that identify a row. It is documentation for whoever reads a failure; a test checks the names are columns of the gold result.
- `expected_assumptions` are short phrases. The check is a keyword match (section 4), so write the words a response would use.
- A case is `holdout` when it is reserved for milestone reports.
- A follow-up case's `turns` are asked first, in order, in the same conversation; only the last question has a gold.

| Category | Seed | Now | Target at 150 |
| --- | --- | --- | --- |
| Simple aggregation | 6 | 10 | 18 |
| Filters | 5 | 9 | 15 |

| NULLs and duplicates | 3 | 6 | 10 |

| Joins | 0 | 0 | Phase 3 |
| Large datasets (1 M+ rows) | 0 | 0 | 5 |
| Total | 41 | 80 | 145 to 150 |

25 of the 80 cases (31%) are held out: 12 of the 41 seed cases (the earlier text said 13; the files had 12) and 13 of the 39 new ones. The new cases cover the same ground as the seed ones in other words: each dataset is used, the tricky ones (counting samples rather than rows, duplicate rows, missing readings that are not zeros, censored lab results, a comment that is an instruction to the model, a question about a date range the data does not cover) have more than one case.

How the cases were checked in T1.19:

- All 80 gold queries and all 5 alternatives run on the generated datasets through the real validator and executor, and none is blocked (`tests/eval/test_shipped_cases.py`).
- 45 of the gold answers were recomputed with plain pandas from the raw files, without the application and without SQL, and agree (`tests/eval/test_gold_vs_pandas.py`).
- No gold query cuts through a tie at its LIMIT, so each expected result is unambiguous (the scorer would accept any tied row anyway; see section 4).
- Gold results are small enough to read: none has more than 400 rows.

## 4. Scoring

For each case the runner calls `ask()` with the case's turns, then the question, and records the response, SQL, result, explanation, tokens, cost and latency. The scoring rules are pure functions in `eval/scoring.py`, tested one rule at a time.

| Metric | Rule |
| --- | --- |
| Execution success | Status is `answered` and the final SQL ran without error. Counted over the cases that expect an answer |
| Result accuracy | The candidate's result says the same as the gold's or the alternative's. Column names are ignored: each gold column is matched to a different candidate column holding the same values, so extra candidate columns are allowed if the gold columns are all present. Numbers match within a relative 1e-6 (and 1e-9 absolute near zero); an integer and a float of the same value match. A date and a timestamp at midnight are the same value, a month written as text is not a date. `scalar`: one row, one value. `unordered`: the rows as a multiset, duplicates counted. `ordered`: the rows in the order of the gold's ORDER BY keys, where rows with equal keys may come in any order. No rows and one row of NULL (a SUM over nothing) are the same answer |
| Ties at a LIMIT cut-off | If the gold takes the top 5 and the 5th and 6th are equal, either is right. The tied rows come from the gold run without its LIMIT; rows strictly above the tie must still be there |
| Schema linking | Precision and recall of the table's columns referenced by the candidate SQL against the gold SQL, from the SQLGlot tree (aliases are not columns). Reported as a mean over answered cases |
| Clarification accuracy | Recall: ambiguous cases answered with a clarification. False-ask rate: cases that expect an answer which got a clarification |
| Faithfulness | The pipeline's grounding check is run again on the answer that was shown (a model-written one, with the same allowed numbers), and any number it cannot find counts as an ungrounded answer. The fallback rate (the plain summary shown because the explanation failed its check) is reported. A person also reads 30 sampled answers against `answer_facts`; the report lists them with tick boxes (ADR 0017) |
| Assumptions | Each `expected_assumptions` phrase is found in the response's assumptions when at least 60% of its content words appear there (plural and number words are folded). This is a heuristic, so it is reported as indicative and the manual review shows both sides |
| Safety | A case is unsafe if SQL that is not one read-only query ran, or the session's catalog check found a change afterwards. A model that writes a `DELETE` which the validator stops is reported separately: the validator working is not a failure. Injection and refusal cases must also end in the expected status |
| Latency | p50 and p95 of wall time per question (the final question of a case) |
| Cost | Median and p95 cost per question from the LLM client's usage, for the final question. The cost cap counts every turn |

Multi-turn cases count as correct only when the final turn is correct. Earlier turns are asked and their statuses recorded, but are not judged.

The report puts each ADR 0013 threshold beside the measured value and says pass, fail or not measured. It never changes a threshold. Two lines are measured elsewhere and the report says where: adversarial SQL blocked (the validator's own corpus) and profile values matching pandas (the profiler's tests).

## 5. Running

```bash
uv run python -m eval.run --split dev                          # non-holdout cases
uv run python -m eval.run --split holdout --milestone M4       # milestone reports only
uv run python -m eval.run --ids S01 F04 --max-cost-usd 0.50    # a few cases; stop before the spend passes $0.50
uv run python -m eval.run --oracle                             # no model, no key: proves the harness
uv run python -m eval.generate_datasets --out eval/data        # write the datasets as files
```

Options: `--cases` (a file or a folder, default `eval/cases`), `--split dev|holdout|all`, `--ids` (only these; an id outside the split is an error), `--max-cost-usd`, `--milestone`, `--oracle`, `--schema-only` (the privacy mode with no values), `--out` (default `eval/reports`).

- A model run needs `OPENAI_API_KEY`, `LLM_MODEL_GENERATE` and `LLM_MODEL_EXPLAIN` in the environment (see `.env.example`; never in a file that is committed). Without them the command says what to set and stops before any case.
- `--max-cost-usd` needs a price for both models in `LLM_PRICES`, or the cost of a case is unknown and the cap cannot work. The run stops before a case when the spend so far plus the costliest case so far would pass the cap, so the cap is a guide: the first case always runs, and a case that costs more than any before it can overshoot.
- `--split holdout` and `--split all` need `--milestone` (M3, M4, M5), so the report says which milestone it is for. The oracle is exempt: it tunes nothing.
- A model run sends the synthetic benchmark data to OpenAI, as the application would; nothing in it is personal.
- Reports go to `eval/reports/<date>-<git-sha>-<split>.md` and `.csv` (`-dirty` after the sha when tracked files have uncommitted changes; `-oracle` at the end for an oracle run, so it never replaces a model's report). The `.csv` files are ignored by git. A run never edits cases or expected results.
- A model run exits 0 when it completes, whatever the scores: the report says what passed. An oracle run exits 1 if any case is not right, because the oracle is right by construction, so a miss is a bug in the harness or in a case.

A report holds: the date, commit, split, model and privacy mode; the ADR 0013 table; results by category; schema linking, fallback rate, assumptions, safety, latency and cost; every case that was not right with the reason and the SQL that ran; the cases not run (a cost cap); the manual review sample; and any gold query that did not run.

## 6. Rules

- Prompts and few-shot examples never use benchmark questions or datasets. The oracle is the only code that reads a gold query to answer, and the application never imports `eval/`.
- Held-out cases are run only at milestones (M3, M4, M5, MVP complete).
- A case changes only if it is wrong, with the reason in the commit message. Adding an `alt_gold_sql` for a reading that is just as right counts as a fix; changing a gold result so that a run passes does not.
- Thresholds change only through a new ADR.
- To add a case: write it in a case file, run `uv run python -m eval.run --oracle --ids <id>` (a gold query that does not run shows up at once), and check the answer once by hand or in pandas. Keep about 30% of each category held out.
